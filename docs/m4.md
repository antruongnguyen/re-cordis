# M4: typed publication and injection convergence

This records the M4 boundary. [M5](m5.md) now adds isolated slots, bound calls,
typed reflection/hooks and config updates; statements below assigning those
features to M5 describe the historical milestone split, not current absence.

**M4's global-slot service slice is implemented.** This adds typed named
publication, checked/direct lookup, per-Fiber injection declarations, dependency
convergence, and exact-provider retention to [M3](m3.md). Rust 2024, the tested
Rust 1.85 minimum, explicit local hosting, and the existing dependencies remain
unchanged.

This is not complete Reflect/Service suite parity. Isolation realms, intercept
metadata, bound use-site tracing, accessor/mixin/associated/callable equivalents,
configuration updates/recovery, and internal get/set/service/status/update hooks
remain M5/M6. Explicit plugin apply replaces implicit constructor/Service.init
discovery; no JS property or class reflection is simulated.

## Public surface

| API | Contract |
|---|---|
| `ServiceKey::<T>::new(name)` | Name selects the slot; T is a checked value contract, not part of slot identity. Different names may have the same T; incompatible contracts for one name return `TypeMismatch`. |
| `key.required()` | Produce a heterogeneous-list-compatible required `Dependency`. |
| `Context::provide(&key, value)` | Immediately register one Fiber-owned publication and its cleanup effect. Duplicate current providers are errors, including a second publication from the same Fiber. |
| `Context::provide_checked(&key, value, check)` | Add a synchronous readiness predicate. False blocks injection. Errors/panics are diagnosed against the provider and block injection without failing the consumer. |
| `Context::set(&key, value)` | Only the exact providing Fiber may change the current publication's value. Preserve its identity; do not notify/reload consumers or recheck readiness. |
| `Context::get(&key)` | Checked own/injected lookup, with the root's explicit unchecked bypass. Returns `Result<Option<Rc<T>>, ServiceError>`; a root read of an absent name returns None. |
| `Context::get_direct(&key)` | Explicitly bypass injection authority, but require an Active, unpaused provider. Missing/inactive returns None. |
| `Context::get_unchecked(&key)` | Explicit direct lookup including Loading/Unloading providers still occupying the slot. This does not retain lifecycle resources. |
| `Plugin::injecting(dependencies)` | Set the declaration view's required injections. Clones share Plugin grouping identity; each spawned Fiber captures its own list. |
| `Context::inject(dependencies, apply)` | Create a parent-owned no-config consumer with the same lifecycle semantics as a declared Plugin. |
| `ServiceRegistration::id()` | Read an opaque `PublicationId`. Equality identifies the exact publication, not its value or provider. |
| `ServiceRegistration::withdraw()` | Claim the effect now, remove only this exact current publication, notify consumers, then await its old dependent loads' cleanup. Dropping its waiter does not cancel it. |
| `ServiceRegistration::into_effect()` | Transfer publication cleanup through the existing `Disposer::from_effect` composition protocol. |

Publication tokens have inert Drop, like effects/listeners. A dropped token
remains owned by its registering Fiber. Failed host/owner admission does not
publish a value. Names such as `__proto__` are ordinary string keys.
An explicit `Option<T>` value represents an upstream undefined service value;
publication presence remains distinct from the optional value.
`ServiceError` distinguishes admission, duplicate provider, type mismatch,
undeclared access, inactive declaration, missing provision, and wrong owner.

See the runnable service example and compile-fail contract example in
[`ServiceKey` Rustdoc](../crates/re-cordis-core/src/service.rs).

## Checked access and value changes

Starting from a non-root definition Context, look for the newest matching own
provision, then its committed injection if that Fiber declares the name.
Otherwise walk the parent Fibers. An own provision wins over that Fiber's
injected view. An inactive nearest declaration is an error, not permission to
fall back to another live provider. Ancestor own provisions, including root
provisions, are inherited as in upstream `locate`.

Root starts with unchecked direct access. Calling a service that explicitly
captures a plugin Context still uses that captured Context's authority; a root
caller cannot turn it into root access. Full automatic method/accessor tracing
and use-site effect attribution are not implemented.

Reads clone an `Rc<T>` of the value currently stored in the selected publication.
Set changes that value for later reads, including reads through committed
injections; it does not mutate previously returned `Rc<T>` values. Such values
are not lifecycle leases. To survive provider teardown, cleanup must belong to
a committed injecting Fiber, not merely retain a direct lookup result.

Withdrawal followed by provide always creates a different publication, even
when both values are equal or are clones of the very same `Rc`. Old cleanup
continues to read the old publication. Its completion cannot erase a newer
publication under the same name.

## Resolution and convergence

An injection requires an available provider of the declared type. Provider
apply must finish before it becomes available; publication during Loading
does not activate consumers. Missing providers or false readiness leave the
consumer Pending, with source validation deferred. An incompatible available contract
fails explicitly and preserves its structured service error as the lifecycle
callback source.

Service notifications update only the affected candidate names. Explicit
restart reuses those candidates and changes the restart revision; it does not
rerun unrelated readiness checks. A readiness predicate whose external state
changes needs a service availability notification or republication, not set.
There is no public internal-service hook/notification protocol yet.

A target consists of restart intent plus exact candidate publication identities.
Before validation/apply, commit the dependency snapshot and attach the Fiber
to those publications. Retain it across asynchronous apply, partial rollback,
pending effect acquisitions, final acquired disposers, children, and cleanup.
Only after that load's entire cleanup barrier are its provider dependencies
released. Self-provisions do not create a self-wait.

One existing supervised driver converges toward the latest target. Intent
changes during apply do not abort it; obsolete resources are collected and
drained. Changes during unload do not interrupt cleanup; only the latest
available target loads afterward. An obsolete failure is reported without
poisoning the latest target. Failed Fibers do not retry on dependency refresh;
configuration-update recovery remains M5.

`ready()` observes one Fiber's current settlement, which can be Pending. It is
not a runtime-wide convergence barrier. Joining a provider's restart does not
automatically join every consumer's new load; await those consumers separately.
Terminal disposal still wins over queued restart/dependency intent.

## Retention, cleanup, and ownership

```text
Runtime -> current named publication table
Registry / parent cleanup / driver -> Fiber -> Owner
Owner -> current and withdrawing own publications
Owner -> committed exact dependency publications
publication -> dependent Fiber identities + release notification
publication --weak--> provider Owner
Context / publication cleanup --weak--> runtime and owner
child Owner --weak--> parent Owner
```

Withdrawal bars new consumers synchronously before waiting. Each publication
waits only for its exact dependents, including consumers already removed from
the Registry. It does not wait for another publication from the same provider,
or for a consumer's replacement setup. Old targets are discarded on failure/
disposal rather than retaining unnecessary snapshot values in public handles.

An unloading provider stops admitting consumers and waits for dependents of
all its current and already-withdrawn publications before draining resources.
Transitive providers therefore retain their own injections while their
consumers drain. Children that inherit a parent's injection finish before
that parent's snapshot is released; a child explicitly injecting its parent's
service is independently notified to unload before the parent waits for it.

Whole-journal drains, including root's reusable snapshot drain, temporarily
pause service availability without changing a plugin's public state.
New registrations still belong to the next snapshot. Existing exact dependents
finish before resources/listeners are cleaned; services registered for a later
snapshot become available when the drain completes.

Top-level cleanup remains concurrent across unrelated owners and independent
effects. Publication effects still compose in reverse sequential order, so
putting withdrawal after resource acquisition in a composed effect keeps the
resource alive through withdrawal. Manual cleanup is not a new global
serialization mechanism.

Storage borrows do not span user checks, callbacks, destructors, or awaits.
Drains do not hold an owning executor reference across their waits. Host
destruction cancels outstanding lifecycle/cleanup work and is not successful
async teardown. Existing self/ancestor lifecycle refusal and all other
[M1](m1.md)/[M2](m2.md)/[M3](m3.md) cancellation restrictions remain.

## Evidence and remaining cases

The suite now has **100 integration tests**, including **28 M4 tests**, and
**ten Rustdoc checks**. Tests use channel gates and bounded waits, not sleeps.

| Pinned behavior | Integrated evidence |
|---|---|
| `reflect.spec.ts`: access check and inject leak | `tests/services.rs`: explicit owner/access/type failures, checked versus direct paths, own/inherited provisions, and inactive committed declarations. JS special property access is replaced by static Rust Context members and explicit service keys. |
| `service.spec.ts`: multiple injections and dependent-before-provider/restart cleanup | Multi-key availability/validation gates and `provider_resources_survive_all_disposal_orders_and_restart`. Async plugin apply provides the initialization barrier, not automatic Service.init. |
| `fiber.spec.ts`: failed Fiber ignores dependency refresh | `failed_consumers_ignore_dependency_refresh_and_mismatches_fail_explicitly`. Pending/Failed terminal snapshots are covered too, but internal/status event sequences are not. |
| `service-dispose.spec.ts`: removed consumers and per-publication withdrawal | `withdrawal_waits_for_a_consumer_already_removed_from_the_registry`, `one_withdrawal_does_not_wait_for_another_publication_from_the_same_provider`. |
| Transitive retention and concurrent cleanup | `transitive_cleanup_retains_providers_while_unrelated_owners_and_siblings_progress`, final provider-listener/error coverage, root-owned resource retention. |
| Setup/rollback and inherited/explicit child cleanup | In-flight apply success/failure variants, pending effect final acquisition/cleanup, ancestor-injection retention, and explicit parent-service injection. |
| Composed effects | Manual and owner-shutdown variants plus inherited own-provision access from a composed child disposal. |
| Replacement races | Old-withdrawal versus gated new setup; current/withdrawn binding shutdown in both completion orders; same-`Rc` replacement during initialization; latest-only replacement during unload. |
| Ownership and regression checks | Twenty repeated publications restore Registry/effect/value baselines; retained disposed/failed handles release dependency values; destroying a host during removed-consumer cleanup cancels waiters. |

The [pinned checklist](m0-cases.md) marks only these integrated contracts or
explicit Rust representations. Both realm-dependent declarations in
`service-dispose.spec.ts` remain unchecked for M5, as do isolated-provider
cleanup, transparent tracing, mixin reflection, and the complete Service.init
protocol. Full `reflect.spec.ts`/`service.spec.ts` parity is not claimed.

Validation uses workspace tests including Rustdoc, formatting, strict Clippy,
current stable, actual Rust 1.85.0 check/tests, and the independent M0 suite.
The final [M6 verification](m6.md#verification) reruns these contracts using
explicit compiler/Rustdoc binaries and isolated artifacts. Earlier label-based
invocations were insufficient to establish which subprocess binaries ran in this
mixed Homebrew/rustup environment. M0 has 20 integration tests and one Rustdoc
check, run separately on both actual compilers in that final audit.
A toolchain name or a separate version probe alone is not build-version evidence.
