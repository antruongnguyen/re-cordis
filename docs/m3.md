# M3: Registry and base plugin lifecycle

This records the M3 boundary. [M5](m5.md) now implements scoped reflection,
typed lifecycle hooks and config updates on [M4](m4.md)'s retained publications.

**M3's base lifecycle is implemented.** The unpublished Rust 2024 core now
admits typed plugin instances, groups them by reusable declaration identity,
validates source config on load, scopes resources to each Fiber, and supports
restart/disposal with parent-owned child cleanup. It retains Rust 1.85 as the
tested minimum and adds no dependencies.

This builds on [M1 hosting](m1.md) and [M2 effects/events](m2.md).
[M4](m4.md) now adds typed global-slot publication/injection and dependency-driven
Pending/Active convergence. Configuration updates/recovery, tracing/intercepts, and internal
update/status hook protocols remain M5. The six-state vocabulary is not a
claim that those later transitions or all upstream tests already exist.

## Public surface

| API | Contract |
|---|---|
| `Plugin::new(name, apply)` | A reusable `Plugin<C>` with identity validation. Source `C: Clone` is cloned into apply; each spawned instance retains its own source. |
| `Plugin::validated(name, validator, apply)` | A `Plugin<C, R>` with synchronous `&C -> Result<R, E>` validation and an apply factory returning a local future. A source can be non-Clone here. Validation runs on every load, not before registration. |
| `Context::plugin(&plugin, source)` | Admit synchronously, commit Registry residency and parent cleanup ownership, schedule the initial pass, and return a typed `FiberHandle<C>`. It does not await validation or apply. |
| `FiberHandle::id/name/state/config/context` | Opaque stable identity, captured diagnostic name, last observed state, retained `Rc<C>` source, and non-owning Context. The resolved `R` is passed to apply, not stored as source. |
| `FiberHandle::ready()` | Return a wait-only barrier for the current pass; self/ancestor lifecycle waits from apply/cleanup are refused. A terminal or settled handle can be inspected without starting work. |
| `FiberHandle::restart()` | Force unload/reapply of the same source and same identity. Requests during a pass coalesce toward the latest revision; a failed Fiber retains its failure until a future config-update API clears it. |
| `FiberHandle::dispose()` | Mark terminal and unlink Registry/parent ownership now; finish in-flight apply, partial rollback, children, and resources before the Disposed barrier. Repeated calls do not repeat cleanup. |
| `Context::registry()` | Non-owning typed Registry control and read access. |
| `Registry::len/is_empty/contains/instances` | Read current group presence/count and snapshot instance identities. These are not mutable runtime records or callback-pointer reflection. |
| `Registry::remove(&plugin)` | Detach the current group and synchronously start disposal of its members. Return one wait-only `LifecycleTask` per member; await them to join teardown. |
| `Context::name()` / Debug | Read the selected Fiber's diagnostic name; Debug renders `Context <name>`. Empty plugin names inherit the nearest named parent, falling back to root. |

`Plugin` clones share identity. Two separately constructed declarations do
not group merely because their callbacks have the same Rust type or name.
The declaration is immutable, so name/validator are shared consistently;
there is no mutable JavaScript function metadata or first-spawn mutation API.
Rust function/object/class-shaped application behavior is adapted explicitly
to the typed apply callback. Invalid plugin shapes/config argument types are
compile errors, not late runtime discovery. There is no implicit constructor
or `Service.init` reflection.

Apply returns `Result<(), E>` and registers its acquisitions explicitly with
the Context's effect APIs. `ctx.effect`, async setup/stream setup, listener
registrations, exporters, and ordinary cleanup all attach to the selected
Fiber, not automatically to root. `ctx.root()` deliberately selects root and
discards derived metadata. Capturing the supplied Context does not keep the
runtime or its cleanup owner alive.

An executable Plugin Rustdoc example demonstrates create/ready/restart/dispose.
The existing [M1 validation commands](m1.md#run-and-validate) still cover the
workspace and independent M0 package.

## State and concurrency rules

The public states are Pending, Loading, Active, Failed, Unloading, Disposed.
At the M3 boundary every plugin was unconditionally runnable and Pending was
only an initial position. M4 now captures injection declarations per Fiber,
leaves missing dependencies Pending without validation, and schedules Loading
only when all required publications are available.

One supervised driver per Fiber owns apply/cleanup at a time. A revision
records restart intent; concurrent requests update that target instead of
starting overlapping apply calls. A post-driver recheck closes the gap between
worker completion and supervisor publication. A restart during unload waits
for that cleanup before loading the latest revision. A restart during apply
drains that apply's acquisitions before reapplying the unchanged source.
No FIFO ordering across unrelated Fibers is promised.

The source is validated at each actual load, then resolved input is passed
to the apply factory/future. Callback errors and user panics are normalized
with their original error source retained. A failure reports diagnostics and
rolls back partial effects before publishing Failed. A failed initial Fiber
remains resident/addressable until disposal; creation does not hide it behind
an error with an unreachable instance. If an obsolete apply fails after a
restart, its error is reported and cleaned up without poisoning the later
revision. Config-update recovery is not yet implemented.

Terminal disposal wins over uncommitted restart intent. It removes Registry
residency before awaiting cleanup, but the driver keeps the Fiber alive while
it drains. Apply already in progress is not forcibly aborted. Once terminal,
new effect/listener/exporter/plugin registrations through that Context return
`InactiveContext`. Existing cleanup can still dispatch events or log; those
operations do not create a new registration. `ready`/restart/dispose waiters
receive the latest pass's terminal result, not an abandoned earlier target.

Cleanup failures are reported but do not prevent independent cleanup or the
Disposed barrier. A framework driver panic is a separate `DriverPanicked`
failure, not a successful callback result or an automatic repair attempt.
As with M1/M2, process abort, hostile destructor panics, and executor destruction
cannot promise completed cleanup.

## Parent ownership, Registry residency, and weak ancestry

```text
Runtime State -> Registry group -> resident Fibers
Fiber -> its Owner -> resource cleanup journal
parent Owner -> child-disposal cleanup -> child Fiber
Fiber --weak--> its Registry group and parent effect owner
child Owner --weak--> parent Owner
Context / Effect --weak--> State and selected Owner
driver -> State + Fiber until its barrier
```

The child's disposal is an effect in its spawning Context's journal, labeled
`ctx.plugin()`. Parent unload/restart/root drain therefore cascades to the
child tree. Explicit child disposal removes that parent effect immediately,
preventing a long-lived parent from accumulating already-disposed children.
Dropping public Fiber handles is inert; residency and parent ownership remain.
The Registry retains live/failed instances, not merely weak handles.

Group removal detaches one exact allocation. New instances of the same
declaration form a fresh group; old cleanup cannot prune or dispose that new
group. Read snapshots expose identities, not ownership authority or internal
collections. Every storage borrow is released before user callbacks,
destructors, or awaits.

Typed Context metadata ancestry is separate from lifecycle ownership. Parent
owner links are weak and are used only for callback attribution/refusal.
Direct lifecycle self-waits and waits on an owning ancestor are refused before
admission instead of deadlocking the subtree. This is an explicit safety
restriction relative to TS, not a new upstream guarantee. User-spawned tasks
do not inherit callback attribution or host admission automatically; passive
waits from arbitrary user task graphs are not a general deadlock detector.

`Context::drain()` drains its selected resource journal without changing the
plugin's state; lifecycle control belongs to the FiberHandle. Root drain
remains reusable and also claims child-disposal effects. A completed drain
is a snapshot barrier, not a runtime-wide shutdown primitive or a join of
previously manually claimed work.

Context metadata, name, and IDs remain readable after Runtime drop, including
the cached root identity returned by `root()`. New operations then return
`RuntimeDropped`. Dropping the host cancels in-flight lifecycle work and its
waiters observe HostStopped. A retained FiberHandle may retain its source,
definition, metadata and outstanding cleanup captures until the handle is
dropped; dropping the host does not pretend those async cleanups ran. Applications
must explicitly dispose/join desired instances before host shutdown. This does
not collect arbitrary user-created Rc cycles (including self-captured handles).

## Diagnostics and resource scope

Listener/exporter removal resolves the exact owning journal. Tokens surviving
automatic disposal can be removed harmlessly even after that owner is released.
Snapshot event callbacks remain selected, including during final cleanup.
Setup rollback uses the same owner-specific recursion rules as disposal.

Log records use the current Fiber identity. Default logger names now use the
captured Fiber name; explicit names still override it. Plugin load, setup, and
cleanup diagnostics retain that owner's identity. Raw diagnostic names are
not yet fully normalized as TS names are, and service-call naming/intercept
defaults still require M5/M6. Event-level diagnostics without a selected callback
owner continue to use runtime/root attribution. The built-in buffer survives
root drains and exporters remain scoped to their registering Fiber.

## Evidence and remaining source coverage

At the M3 boundary the production suite contained **72 integration tests** (21 M3 plugin tests
plus the prior 51), and **eight Rustdoc checks**. There are still no additional
dependencies or new test tools. Deterministic channel gates exercise:

- Shared declaration grouping, independent source/instance identity, immutable
  validation definitions, and exact empty-group pruning.
- Structured validation errors, per-load resolved config, apply errors/panics,
  Failed-after-rollback, and successful independent instances.
- Parent/child/grandchild listener cleanup, root listeners surviving child
  removal, inherited metadata/names, and reusable root teardown.
- Restart coalescing during cleanup/apply, superseded apply failure, and
  disposal beating queued validation/restart while waiters are abandoned.
- Removal/recreation of a group during gated old cleanup, repeated effect/
  listener baseline restoration, and immediate parent-registration unlinking.
- Scoped async acquisitions/exporters, inactive contexts, final cleanup dispatch,
  resource release with retained disposed handles, and observable host cancellation.
- Direct self/ancestor lifecycle refusal, harmless expired registration tokens,
  and typed compile-fail rejection of invalid plugin/config shapes.

The cases live in [`tests/plugins.rs`](../crates/re-cordis-core/tests/plugins.rs).
The pinned cases newly mapped by this milestone are:

| Pinned source cases | Integrated evidence / representation |
|---|---|
| `plugin.spec.ts`: functional/object apply, invalid plugin | Grouped declaration/config tests and `typed_object_method_adapter_keeps_config_and_cleanup_with_its_instance`; invalid shape/config compile-fail examples in `Plugin` Rustdoc. |
| `plugin.spec.ts`: inactive Context and Context inspection | `disposing_child_rejects_new_work_but_final_cleanup_can_dispatch`, plus captured names, Debug, root reset, and expired-owner checks. |

The [pinned checklist](m0-cases.md) marks only supported cases and explicit Rust
representation equivalents: typed plugin adapters replace function/object shape
reflection and runtime validation of invalid plugin values. Registry operations
are typed replacements, not an identical JS Map API.

M4 now covers dependency-driven Pending and service-driven restarts.
Config updates/recovery,
`internal/status`/`internal/plugin` observations, per-Fiber `internal/update`
middleware, and `Service.init` remain unchecked for their owning milestones.
In particular, observing a matching state via `state()` is not evidence for
the upstream status-event transition sequence. See M4 for the current production
test totals and exact-publication retention built on these owner/residency relations.
