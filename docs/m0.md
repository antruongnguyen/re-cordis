# M0: behavioral baseline and design-spike results

Date: 2026-10-23. **M0's design-spike pass is complete.** The later production
foundation is documented in [M1 contracts](m1.md).
The executable evidence lives in [`spikes/m0`](../spikes/m0/), a standalone,
unpublished Rust 2024 package. These are deliberately separate test models,
not an initial implementation of `re-cordis-core` and not a public API promise.

The specification is TypeScript Cordis at
[`35fdc969e4b6c48c48ed44717c7a018324e4dd88`](https://github.com/cordiverse/cordis/tree/35fdc969e4b6c48c48ed44717c7a018324e4dd88).
The [case checklist](m0-cases.md) inventories all 144 named test declarations
across its 15 core spec files, plus the event type-checking suite. Parameterized
declarations retain their variant requirement. Unchecked entries mean that
production parity is still pending, not that M0 needs to implement all of core.

## Reproduce

Run from the repository root:

```sh
cargo test --manifest-path spikes/m0/Cargo.toml --locked
cargo fmt --manifest-path spikes/m0/Cargo.toml --check
cargo clippy --manifest-path spikes/m0/Cargo.toml --all-targets --locked -- -D warnings
rustup run 1.85.0 cargo test --manifest-path spikes/m0/Cargo.toml --locked
```

The package keeps its own resolver-3 workspace and committed lockfile, excluded
from the later root production workspace. Its dependencies are dev-only: Tokio
for local tasks/channels and test watchdogs, futures for joining, polling,
and callback-unwind containment. No schema, serialization, macro framework,
new test runner, or copied prior-port implementation is needed.

Evidence: **20 integration tests and one compile-fail doctest**, run with Rust
1.98.1 and genuine Rust 1.85.0. The initially listed `1.85` toolchain was
incomplete and fell back to Homebrew's compiler; it was not counted as MSRV
evidence. An actual `1.85.0` toolchain was restored and its version verified.
The spike's declared `rust-version = "1.85"` is supported by that run. This is
not yet the production workspace's MSRV guarantee.

## Gate A: local execution and explicit lifecycle ownership

**Decision for M1:** start local-first with Tokio and an explicitly hosted
`LocalSet`, `Rc` handles, and non-Send futures. The host must remain driven
until explicit drains finish. Do not introduce an executor trait, thread-safe
API bounds, or a hidden fallback runtime without evidence they are needed.
The spike assumes an entered LocalSet; production construction must make the
host explicit instead of panicking after partially publishing work.

Lifecycle requests are ordinary synchronous methods that commit admission
and schedule work before returning a completion handle. Dropping that handle
does not cancel the operation. Creation in this model also commits residency
and parent ownership synchronously; there is no lazy creation future and no
unowned gap before handle delivery. Async validation/preparation, if ever
added, would require a new precommit boundary rather than silently changing
this rule.

The ownership graph is intentionally one-way:

```text
application -> Runtime -> resident Fibers
                        -> service slots -> exact Bindings
parent Fiber -> child Fibers
consumer Fiber -> committed Binding
Binding --weak--> dependent Fibers
local lifecycle task -> Runtime + draining Fiber until completion
```

No child-to-parent ownership edge is needed by this lifecycle model. The
separate typed-access model uses definition ancestry with weak provider
backreferences; M1 must integrate the two without introducing a strong cycle.
User callbacks must not capture their own owning Fiber strongly; the tests
use weak captures and prove release after explicit teardown. This is not a
claim that arbitrary user closure cycles can be collected.

| Runnable test in `tests/lifecycle.rs` | What it proves |
|---|---|
| `withdrawal_returns_consumer_to_pending_then_rebinds` | Missing dependency means Pending; arrival activates; retirement drains; equal-value replacement has a different exact binding. |
| `pending_consumer_keeps_exact_binding_through_removed_consumer_cleanup` | A Registry-removed consumer keeps its provider open through gated cleanup; new consumers see a replacement, not the retired binding. |
| `individual_withdrawal_does_not_wait_for_another_binding` | Withdrawing foo does not wait for a blocked bar consumer from the same provider. |
| `same_fiber_cleanup_request_is_refused_before_admission` | Same-owner cleanup recursion is refused rather than deadlocking; an equal numeric ID in a different runtime is not falsely refused. |
| `transitive_provider_chain_drains_from_leaf_to_provider` | A gated leaf finishes reading bar before its relay finishes reading foo; the root drains the whole chain without deadlock. |
| `parent_cascades_root_reuses_and_dropped_waiter_does_not_cancel` | Parent owns children; abandoned waiters do not abandon cleanup; repeated root disposal leaves root usable; weak probes show release after teardown. |
| `top_level_cleanup_is_concurrent_attempt_all_and_exactly_once` | A gated cleanup does not block sibling invocation; another error and callback panic are reported; repeated disposal does not rerun cleanup. |
| `composed_cleanup_sequences_async_children_in_reverse_order` | Inside a composed effect, reverse-order cleanup waits for an async child before running the next child. |
| `executor_shutdown_is_not_a_cleanup_completion_guarantee` | Destroying the LocalSet cancels pending work; waiters observe cancellation, not successful cleanup. |

Same-Fiber lifecycle requests from cleanup are refused with an explicit error
before admission. This is a deliberate safety restriction relative to TS's
possible self-wait, not a parity claim. Attribution follows the allocation,
not its runtime-local numeric ID. The model checks directly attributed cleanup;
raw user-spawned tasks do not inherit that task-local marker. M3 must cover
setup/restart/update attribution when the complete lifecycle driver exists.

Top-level cleanup snapshots are taken out of storage before callbacks run.
Returned user errors and user callback panics are reported at that boundary,
not ignored. Framework invariant assertions are outside that catch. The
prototype stores diagnostic text for inspection; preserving typed error
sources, panic payload formatting, and detached invariant-task supervision
remain production implementation obligations, not reasons to catch all panics.

**Ceilings:** the lifecycle model has one required named service per Fiber,
synchronous setup, and only Pending/Active/Unloading/Disposed states. It does
not implement update/restart arbitration, async setup rollback, Failed state,
registration gates during all phases, built-in hooks, logger persistence,
or cyclic dependency diagnostics. Those cases remain assigned to M2-M5.
Disposed child handles stay in the parent's model list until its next drain;
production unlinking must release them promptly rather than accumulating them.
There is no claim of completion after executor destruction: applications must
await teardown before stopping the host. A secondary completion runtime is
not justified by this experiment.

## Gate B: typed keys and explicitly bound service calls

**Decision for M1:** keep name/type contracts, isolation labels, publication
occurrences, plugin grouping identity, and Fiber identity distinct. Use
checked `Any` downcasts internally and explicit access operations rather than
simulating property reflection. Retain isolation-boundary history, not merely
the final label map. `TypeId` alone is not service or plugin identity.

The `tests/access.rs` model gives a bound service both its provider's definition
view and the consumer's use view. Enter service methods via
`bound.call(|service, call| ...)`; nested lookup uses definition authority,
while configuration and effects use the traced usage view. Explicit accessor
helpers can reuse this path. No proc macro, dynamic property trap, or implicit
method rebinding is required for this API candidate.

| Runnable test | What it proves |
|---|---|
| `nearest_inject_own_provisions_and_same_label_boundaries` | Nearest inject declaration wins, same-label re-isolation blocks inherited authority, own provisions do not borrow injection config, inactive differs from undeclared, direct lookup is visibly separate. |
| `nested_calls_keep_definition_authority_and_use_site_intercepts_and_effects` | Nested calls retain definition checks and injection config while use-site intercepts override layers and nested effects attach to the consumer; entry from root does not grant a plugin-defined method root authority. |
| `typed_extension_and_explicit_accessor_keep_inherited_metadata` | Typed metadata inherits and shadows without mutating the parent; an explicit accessor keeps checked lookup and use-site effect attribution. |
| `named_type_contracts_shared_labels_and_plugin_identity_are_distinct` | Same value type supports distinct names, shared labels select one slot, wrong types fail explicitly, and separately allocated plugin identities do not collapse by Rust type. |

One source-level ambiguity was resolved by reading `ReflectService.provide`
and `_getImpl`: upstream indexes storage by isolation symbol alone. Reusing
one label across different names aliases the slot; adding the name to the
storage key would silently change behavior. The spike demonstrates that
aliasing, with explicit type-mismatch errors when alias contracts differ.
Those errors are a deliberate Rust type-safety restriction, not a promise of
JavaScript's unchecked heterogeneity.

**Ceilings:** this lookup model snapshots one value and does not model active
provider checks, publication mutation, lifecycle-driven invalidation, custom
intercept merge functions, `noShadow`, tracked returned objects, or associated
property setters. Dynamic mixin/accessor/association syntax will be explicit
methods or extension traits; M5 must prove their full behavior. The prototype's
weak provider frame relies on lifecycle residency retaining the definition
while it is usable. It is not safe to treat a raw `Rc<T>` from direct lookup
as a trace-bound service handle.

## Gate C: honest dispatch and source/resolved config

**Decision:** represent bail/serial continuation explicitly with `ControlFlow`;
`Break(0)` and `Break("")` are real results. Sync emit invokes callbacks now
and returns sync errors now. Async listeners use an explicit split adapter:
the callback performs its prefix synchronously and returns the continuation
future, which emit schedules without awaiting. A native `async` closure's
body is lazy, so this is an ergonomic restriction, not automatic JS parity.

`bail` is restricted to synchronous listeners and rejects a mixed snapshot
before invocation. Use `serial` for async responses. This intentionally does
not emulate JS bail returning a promise as a bailed value. Parallel waits for
every outcome and aggregates errors; only abandoned emit continuations use
the diagnostic sink.

| Runnable test in `tests/events.rs` | What it proves |
|---|---|
| `emit_is_immediate_snapshot_based_filtered_and_once_reentrant` | Immediate invocation, disposal does not erase an already selected callback, global bypasses filters, prepend ordering is represented, recursive once is removed before invocation. |
| `split_async_emit_starts_prefix_now_and_reports_detached_failure` | Prefix runs before emit returns; later failure is observed by the sink; mixed async bail is explicitly refused. |
| `parallel_waits_for_all_failures_and_serial_bails_on_zero` | A sync failure cannot short-circuit gated async work; serial stops on zero and sync bail stops on an empty string. |
| `synchronous_error_stops_emit_and_named_contracts_are_checked` | Emit stops at its first synchronous failure; name/argument/result contracts are checked; symbol-like event instances have distinct identities. |
| `waterfall_is_around_middleware_can_veto_and_supports_nested_async_calls` | Sync and async around chains call the tail, unwind outer frames, allow veto, and support nested async dispatch. |

`Next` and `SyncNext` consume themselves on invocation. The `Next` compile-fail
doctest verifies that a second call cannot compile. This deliberately replaces
the TS runtime duplicate-next error with a Rust move error; it does not rely
on a panic or turn waterfall into value reduction. Closures and continuations
are owned; borrowed async continuation ergonomics are not promised.

In `tests/config.rs`, validation is synchronous and returns typed resolved
config or an issue with a structured path. Invalid loaded candidates are
rejected before source replacement, commit notifications, or update middleware.
Pending updates only save source; load validates the latest source. Accepted
middleware sees resolved config without forcing apply, and `noSave` suppresses
commit notification rather than preventing source replacement. The two tests are
`invalid_loaded_update_cannot_reach_middleware_or_mutate_source` and
`pending_defers_validation_and_loads_only_latest_source`.

**Ceilings:** these config/event models are not wired to the lifecycle model.
Internal hooks, middleware ownership across reload, async apply, failed update
recovery, public listener role types, all-mode filtered dispatch, and complete
formatting/schema integration remain future implementation work. Do not copy
the spike's boolean listener options into a public API.

## Agreed traces for production acceptance

These source-backed traces are specifications, not additional passing spike
tests. Their detailed case names are in [m0-cases.md](m0-cases.md).

| Scenario | Required trace / partial order | Owner |
|---|---|---|
| Gated load 1, requests 2 then 3 | Apply `[0, 1, 3]`; clean up 0 and 1 before settling all waiters on 3. | M5, `update.spec.ts` |
| Target changes during unload | Finish old cleanup; do not start load 1; load latest 2. | M5, `update.spec.ts` |
| Old apply fails after supersession | Report old error, clean old effects, allow latest target to succeed. | M5, `update.spec.ts` |
| Latest apply fails | Every waiting update observes latest error after cleanup; no dependency refresh retries Failed. | M3/M5, `fiber.spec.ts`, `update.spec.ts` |
| Provider retires | Final dependent read precedes provider resource close; unrelated cleanup need not wait. | M4, `service-dispose.spec.ts` |
| Disposed during setup | Collect late acquired cleanup, never run an obsolete generator continuation, never load queued config after terminal disposal. | M2/M5, `dispose.spec.ts`, `update.spec.ts` |
| Reusable root drain | Child/user effects disappear; constructor-installed core hooks and default logger buffer remain available. | M3/M6, `context.ts`, `plugin.spec.ts` |
