# M1: production foundations

Date: 2026-10-23. **M1 is implemented.** Subsequent additions and current
restrictions are documented in [M2](m2.md) and [M3](m3.md). The root Cargo
workspace contains only [`re-cordis-core`](../crates/re-cordis-core/), currently
unpublished (`publish = false`). The code is MIT-licensed, uses Rust edition
2024 and Cargo resolver 3, and declares Rust 1.85 as its minimum. The M0
package remains an excluded, independent research workspace.

The M1 scope described here is a small foundation, not the full Cordis runtime:
Context views, runtime/root identity, metadata inheritance, explicit hosting,
and a root cleanup journal. M2 adds effects/events/diagnostic logging, and M3
adds plugins/Registry/non-root Fibers. Service resolution remains unimplemented.

## Run and validate

```sh
cargo test --workspace --locked
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
rustup run 1.85.0 cargo check --workspace --all-targets --locked
rustup run 1.85.0 cargo test --workspace --locked
cargo test --manifest-path spikes/m0/Cargo.toml --locked
```

The workspace and spike lockfiles are committed for reproducible CI. Core's
production dependencies are Tokio (`rt`, `sync`) and futures-util with only
the standard-library/async combinators needed here. Tokio macros/time are
test-only. There is no serialization, schema library, custom executor trait,
multi-thread task requirement, or implicit secondary runtime.

The minimum is justified by edition 2024 and the selected library/language
features, not by copying the prior port's 1.88 requirement. The full suite is
run on genuine Rust 1.85.0 as well as current stable. CI runs checks/tests
and the independent M0 suite on both, with formatting and strict Clippy on
stable. The crate-level Rustdoc example is executable; Context's non-Send
boundary also has a compile-fail doctest. There are 15 integrated foundation
tests and these two Rustdoc checks; M0 retains its separate evidence suite.

## Supported API

| Surface | Contract |
|---|---|
| `Runtime::new()` / `default()` | Construct one independent runtime and permanent root identity; no executor is required for construction. Runtime is an explicit, non-Clone local owner. |
| `Runtime::context()` | Return a cheap non-owning root view. |
| `Runtime::run(future)` | Drive local work from a Tokio block_on/main/test entry point until the supplied future returns. Missing executor, nested hosting, simultaneous driving, and driving from a spawned task are explicit `HostError`s. |
| `Context::runtime_id()` / `fiber_id()` | Opaque comparable/hashable allocation identities. Derived views share them; independent runtimes do not. No numeric representation or ordering contract. Only root Fibers exist in M1. |
| `Context::extend(value)` / `metadata::<T>()` | Add an immutable typed metadata layer; nearest same-type layer wins, other types inherit. A missing value is ordinary `None`. Type-indexed storage and a checked downcast agree by construction. |
| `Context::root()` | Return the same runtime/root identity without derived metadata. |
| `Context::on_dispose(callback)` | Register an owned, one-shot async cleanup returning `Result<(), E>`. The resource is already acquired; setup/generator composition is M2. Drop of its `Effect` token is inert. |
| `Effect::dispose(self)` | Atomically claim this exact registration and schedule it now. Admission failure leaves it root-owned, even though the consumed manual token is gone. A prior automatic claim produces a zero-attempt report rather than duplicate cleanup. |
| `Context::drain()` | Claim the current root journal immediately in reverse registration order and poll callbacks concurrently. Requests during a drain share that pass. Root remains reusable. |
| `Completion` | An awaitable handle to already-started work. Dropping it cannot cancel that work while the host lives. Host destruction reports `CompletionError::HostStopped`, never a successful barrier. |
| `CleanupReport` / `CleanupFailure` | Attempt count plus every returned user error/panic. Completion means the barrier finished, not that callbacks were error-free. Returned errors keep their original `Error::source`, including downcasting. |
| `Runtime::take_failures()` | Take callback failures retained even when their completion waiter was dropped. The same failures remain in the operation's report. |

All handles and callback futures are local, not Send/Sync. Host admission is
task-local and tied to runtime identity. Ordinary spawned Tokio tasks do not
inherit it. Refused registration does not run the supplied callback; callers
must arrange resource rollback if they acquire before an admission failure.

## Ownership and ancestry

```text
Runtime --strong--> State --strong--> root cleanup callbacks
        --strong--> LocalSet --strong--> started worker/supervisor tasks
State --weak--> LocalSet
Context --weak--> State
Context --strong--> metadata layer --strong--> parent metadata layers
Effect --weak--> State
worker/supervisor --strong--> State only until completion
```

Metadata ancestry and lifecycle ownership are separate. A derived Context
keeps its ancestor metadata available but cannot keep the cleanup owner alive.
Registering a callback that captures a Context, including one with derived
metadata, cannot create the internal State-to-callback-to-State cycle that
a strong Context owner would cause. Contexts surviving Runtime drop still
expose metadata/identity, but mutation requests return `RuntimeDropped`.

The host is never retained strongly by its State, Context, or effect token.
Pending tasks can retain State without retaining the LocalSet that owns them;
dropping Runtime cancels tasks and releases their captures. This does not
collect arbitrary user-created Rc cycles or make capturing an explicitly
Rc-owned Runtime in its own callbacks safe.

No storage borrow is held while invoking/polling a callback or releasing a
claimed callback. Typed metadata is immutable. User destructor reentrancy
into registration is covered by an integrated test. Definition-site service
ancestry is not implemented yet: M5 must extend the view model without turning
parent links into a lifecycle ownership back-edge.

## Cleanup, cancellation, and error boundaries

The synchronous request is the commit point; `Completion` is wait-only.
Dropping an unpolled completion leaves the operation scheduled. Dropping a
`Runtime::run` future releases the active-drive guard but pauses its local
tasks; a subsequent run resumes them. Returning from run is not teardown.
Applications must await every started operation they need completed before
destroying the host. There is no executor-independent completion guarantee.

Each root drain snapshots only its current registrations. Cleanups registered
after that snapshot, including from callbacks, belong to the next pass. A
concurrent drain waits for the current pass, not the new registrations. A
manual operation already claimed outside that snapshot has its own barrier;
a root drain is not a runtime-wide join of every manual operation. Retain and
await that operation's completion when needed.

Calling drain from this root's own cleanup returns `ReentrantDrain`, avoiding
a self-wait. Other runtime operations remain separated by host identity. This
is an explicit safety restriction, not a claim about TS's self-wait behavior.
Raw user-spawned tasks are neither attributed nor admitted automatically.

Only callback invocation/polling and user diagnostic formatting have unwind
containment. Returned errors and caught user panics do not skip independent
callbacks. Failed callbacks are never restored to the journal. The default
panic hook can still print panic diagnostics, and aborting builds cannot
recover from panics. Cleanup failures are reported to stderr and retained in
the runtime/report; a broken error formatter cannot erase the original source.
The failure list is not a bounded Logger buffer; callers should take it as
needed until core logging is introduced.

Framework work runs in a supervised task. An unexpected driver panic remains
a task failure, is reported explicitly, and yields `DriverPanicked`; it is not
caught as a successful callback outcome or repaired by retrying cleanup.
Panicking destructors, double panics, process abort, and executor destruction
are not a completion guarantee. Full resource acquisition rollback,
composed effects, async generators, and non-root state transitions belong
to later milestones.

## Integrated evidence and scope boundary

[`tests/foundations.rs`](../crates/re-cordis-core/tests/foundations.rs) covers:

- Independent root/runtime identities, typed metadata inheritance/shadowing,
  root reset, and normal absent metadata.
- Unhosted, wrong-host, nested-host, concurrent-drive, spawned-host, and
  raw-task admission failures without publishing cleanup work.
- Exact manual/automatic claims, inert token Drop, reusable root snapshots,
  concurrent callback progress, and registrations deferred to the next pass.
- Preserved typed errors, callback call/poll panics, formatter panic reporting,
  callback destructor reentrancy, and an unexpected worker panic reported as
  a failed completion rather than successful cleanup.
- Captured Context/ancestor metadata release with and without explicit drains,
  dropped waiters, paused/resumed hosting, and observable host cancellation.

These are integrated M1 foundation checks, not the complete behavior of any
upstream plugin/event/service suite. The [144-case inventory](m0-cases.md)
remains unchecked until those complete cases have production evidence.
M2 adds effect setup/composition, typed events/filtering, and diagnostic logging.
M3 extends those resource APIs to plugin-owned Fibers and records its boundaries
separately. Historical root-only wording above describes the M1 baseline.
