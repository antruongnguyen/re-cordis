# M6: explicit Rust core acceptance

M0-M6's Rust delivery is implemented and reviewed against TypeScript Cordis
`35fdc969e4b6c48c48ed44717c7a018324e4dd88`. The unpublished core remains local,
non-Send, Rust 2024, resolver 3, with Rust 1.85 minimum and no new dependencies.
This is an explicit Rust API, not transparent JavaScript object compatibility.
Checked inventory entries mean tested behavior or a documented Rust
representation, not unrestricted TS parity.

## Logger contract

`ctx.logger(Some(name))` uses the explicit name. Otherwise the nearest use-site
`LoggerConfig` intercept supplies name/level, falling back to the normalized
definition-Fiber name and Info. Names are cached at acquisition. A malformed
intercept makes log operations return `LogError::Configuration`; it is not
silently ignored. `with_level` is an explicit per-handle override, while each
exporter's name/default limit still takes precedence for that destination.

Nested bound calls use the innermost service's definition name and restore
the outer service afterward. Use-site intercepts still override those defaults.
Initialization logs use the initializing Fiber. Automatic non-root diagnostics
now normalize the owner name too; root framework diagnostics retain the existing
`cordis` channel as an explicit diagnostic convention.

Default name normalization follows
[cosmokit 1.8.1 string tokenization](https://unpkg.com/cosmokit@1.8.1/src/string.ts),
the dependency declared by the pinned TS core. It handles acronym boundaries,
hyphens/underscores, and ASCII letter transitions without mutating Context names.
This is source evidence, not a Rust build dependency.

`LogRecord` retains sequence/time/name/level/message, its stable `FiberId`,
and `fiber_ref: WeakFiber`. `snapshot()` returns current value-only lifecycle
metadata, or None after release. Neither retained log records nor Logger handles
retain the runtime or Fiber. Disposed handles can still supply metadata until
their actual allocation is released; root is the permanent reusable owner.

`Logger::log_error(level, ErrorValue)` explicitly represents error metadata:

- Nonempty member lists flatten recursively instead of emitting the aggregate.
- Empty member lists still emit the original error.
- A cause takes precedence over members and is emitted before its outer error.
- Each record retains the exact original error through `failure.source()`.
- Forwarded callback failures preserve their existing diagnostic claim; failed
  initializers and reloads are not re-reported through propagation.

Use `ErrorValue::new`/`from_rc`, `with_cause`, and `with_members` to adapt Rust
errors. Ordinary `log`/`error`/`warn` values use Display and do not dynamically
inspect arbitrary types. Native Error::source graphs require explicit adaptation
when exact independently owned cause records are needed.

Rust `format!`, Display/Debug, and exporter callbacks replace JS printf-style
argument/formatter dictionaries. `record.format(max_length)` truncates each
line to a UTF-16-unit budget and appends `...` only when truncated. CRLF
normalizes to LF and zero remains a real zero limit. Unlike JS slice, it never
splits a Unicode scalar into a lone surrogate. Pass 10240 for upstream's default.
`record.color(text, ColorDepth)` uses the pinned 16/256 palettes and signed
UTF-16 name hash; plain text remains an explicit choice. Formatting/styles
belong to exporter callbacks, not implicit ANSI escapes in the buffer.

The default chronological buffer still keeps exactly 1000 admitted records.
Exporter removal remains exact/scoped, routing is per exporter, and all selected
exporters are attempted on a record even when another fails.

## Initialization and method injection

`Plugin::initialized(name, factory)` is the explicit Service.init counterpart.
The factory returns a future producing one `Disposer`, which may be composed.
Publication during initialization remains unavailable until the factory settles.
Failure rolls back owned effects before Failed, preserves the error source, and
is diagnosed once. There is no runtime constructor/method discovery.

`ctx.inject_method(dependencies, Rc<T>, method)` creates a parent-owned injecting
child. The adapter receives the target and the child's Context, and registers
its effects normally. Provider arrival/withdrawal controls that child; the parent
joins its cleanup. This replaces the decorator's lifecycle behavior without a
proc macro or pretending Rust methods have mutable JavaScript `this`.

## Executable example and type checks

Run the production end-to-end example:

```sh
cargo run -p re-cordis-core --example lifecycle --locked
```

[`examples/lifecycle.rs`](../crates/re-cordis-core/examples/lifecycle.rs) initializes
an isolated store, activates a consumer, updates provider and consumer config
together, skips the obsolete provider/config combination, and asserts final
old-provider reads precede each provider close. Root cleanup restores Registry/
publication baselines while retaining the default logger buffer.
`tests/acceptance.rs` executes that very same code, not a separate mock model.

At the M6 checkpoint there are **146 integration tests** (18 added by M6) and
**17 Rustdoc checks**. The subsequent [lifecycle-parity slice](lifecycle-parity.md)
initially added three Rust integration tests (149 total) and three executed TS
counterparts. The approved bounded failure/recovery extension adds three more:
152 integration tests, six paired scenarios, and the same 17 Rustdoc checks,
without changing production behavior or dependencies.
Counts are not a one-to-one correspondence: integration tests combine source
variants and add independent safety/ownership checks.
The final audit also tests exact service-notification sequences (current
publications only, no duplicate inactive drain notifications), identity-only
filters after their origin runtime is dropped, and lifecycle disposal joining
an earlier journal snapshot before cleaning later-admitted effects and releasing
providers.
Repeated injection names normalize like the upstream dictionary: first position,
last contract/config, rather than retaining conflicting duplicate declarations.
Type checks cover registered-symbol arguments and callbacks/results, typed
service values, source updates, synchronous validators, accessor receivers,
callable arguments, local Contexts, and owned single-use continuations.
Dynamic symbol events use an explicit typed `Vec<hooks::Value>` when
heterogeneous values are needed, not implicit unchecked argument lists.

An initial invocation encountered cached proc macros from Homebrew Rust 1.98.1.
The final audit prepended the selected toolchain's bin directory to PATH,
explicitly set RUSTC/RUSTDOC, and used separate target directories. No shared
build cache was deleted. The same precaution avoids a toolchain label or
standalone version probe being mistaken for evidence of the compiler actually
used by Cargo subprocesses. For example:

```sh
export PATH="$(dirname "$(rustup which --toolchain 1.85.0 rustc)"):$PATH"
export RUSTC="$(rustup which --toolchain 1.85.0 rustc)"
export RUSTDOC="$(rustup which --toolchain 1.85.0 rustdoc)"
export CARGO_TARGET_DIR=target/msrv
rustc --version
cargo --version
rustdoc --version
cargo check --workspace --all-targets --locked
cargo test --workspace --locked
cargo run -p re-cordis-core --example lifecycle --locked
cargo test --manifest-path spikes/m0/Cargo.toml --locked
```

Before running Clippy, also verify
`rustup which --toolchain <toolchain> cargo-clippy` and
`rustup which --toolchain <toolchain> clippy-driver` resolve
inside the selected toolchain. A missing component can otherwise fall through
PATH to an unrelated external Cargo subcommand despite RUSTC/RUSTDOC selection.
If missing, install only that toolchain's Clippy component and rerun; do not
wipe shared caches. The later failure/recovery audit encountered this for
1.85.0, installed its missing component, and passed the complete rerun with
Clippy 0.1.85 rather than Homebrew's compiler.

The M6 checks above execute the Rust production/spike suites, not the upstream
Vitest suite. That checkpoint's parity evidence is source-backed and case-mapped.
The subsequent [lifecycle-parity slice](lifecycle-parity.md) separately executes
six paired Rust/TS scenarios through the pinned upstream Yarn/Vitest setup.
It does not imply execution/parity of all upstream suites or untested JavaScript
dynamic protocols.

## Remaining restrictions and safety deviations

- No transparent Proxy/prototype/class/decorator reflection. Native `Rc<T>`
  reads do not rebind methods; bound adapters must use the supplied Context.
  Virtual get-hook values can be read, but `bind` requires a publication's
  definition identity. Config middleware transforms typed source before
  validation; it does not dynamically replace the validator's Rust contract.
- Local Tokio hosting is explicit. Native futures are lazy; sync/async event
  roles and eager-prefix adapters are explicit. Bail is synchronous-only.
- Drop/executor destruction is not awaited teardown; arbitrary user Rc cycles
  and panicking destructors are not collected/repaired. Self/ancestor lifecycle
  waits from attributed setup/cleanup are refused, not generally detected in
  arbitrary user task graphs.
- Root remains a reusable journal owner. Context drains are snapshot barriers,
  not runtime shutdown/root-plugin restart or joins of separately claimed
  manual effects. Non-root lifecycle disposal does join an existing owner drain
  and then claims later-admitted journal work before releasing dependencies.
- Observer failures and independent exporter failures are diagnosed without
  stranding unrelated cleanup/export. Shared-slot aliases receive dependency
  refresh to avoid name-only withdrawal deadlocks. These are documented safety
  strengthenings, not claims about upstream's failure paths.
- Validation is synchronous Rust code with structured issues, not automatic
  Standard Schema/serde discovery. JS stack-string rewriting, implicit JSON/
  printf formatting, lone surrogates and callable-object syntax are not promised.
- No Send/Sync or executor independence, stable public API, satellite crates,
  native hot loading, implicit runtime creation, or automatic async Drop.

These are compatibility boundaries, not silently completed upstream protocols.
Future integrations should be driven by concrete applications and preserve the
existing source evidence and ownership/cancellation checks.
